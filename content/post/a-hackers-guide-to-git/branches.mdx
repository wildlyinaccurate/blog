Git's branches are often touted as being one of its strongest features. This is because branches in Git are very lightweight, compared to other version control systems where a branch is usually a clone of the entire repository.

<CarbonAd />

The reason branches are so lightweight in Git is because they're just references. We saw in *References* that the `main` branch was simply a file inside `.git/refs/heads`. Let's create another branch to see what happens under the hood.

```
$ git branch test-branch

$ cat .git/refs/heads/test-branch
39f6ea2439eb1fd9f7837a223866f243b70125c0
```

It's as simple as that. Git has created a new entry in `.git/refs/heads` and pointed it at the current commit. Creating a branch doesn't copy anything, doesn't touch your working tree, and takes about as long as writing 41 bytes to disk.

We also saw in *References* that `HEAD` is Git's reference to the current branch. Let's see that in action by switching to our newly-created branch.

```
$ cat .git/HEAD
ref: refs/heads/main

$ git switch test-branch
Switched to branch 'test-branch'

$ cat .git/HEAD
ref: refs/heads/test-branch

$ git branch --show-current
test-branch
```

Switching branches is really two things: updating `HEAD` to point at the new branch, and then updating the index and working tree to match the tree of the commit that branch points to. Since both branches point at the same commit right now, the second part was a no-op.

![main and test-branch both point at commit B. HEAD points at test-branch.](/uploads/a-hackers-guide-to-git/branch-commit-before.svg)

When you create a new commit, Git simply changes the current branch to point to the newly-created commit object.

```
$ echo 'Some more information here.' >> README

$ git add README

$ git commit -m "Update README in a new branch"
[test-branch 5c9d5db] Update README in a new branch
 1 file changed, 1 insertion(+)

$ cat .git/refs/heads/test-branch
5c9d5dbae77c6721433071cf763d8ab26483cb99
```

![After the commit, test-branch points at the new commit C. main still points at B.](/uploads/a-hackers-guide-to-git/branch-commit-after.svg)

`main` still points at `39f6ea2`. Nothing about a branch says "these commits belong to me"; a branch is a pointer to a single commit, and "the commits on a branch" just means every commit reachable from that pointer by following parent links. The same commit can be on many branches at once, and moving a branch pointer is all it takes to change which commits are "on" it. This is the single most useful thing to understand about Git, and nearly everything in the *Merging* and *Rebasing* chapters follows from it.

## Managing branches

`git branch` on its own lists your local branches, with an asterisk next to the current one. Renaming a branch is just renaming the ref.

```
$ git switch main
Switched to branch 'main'

$ git branch
* main
  test-branch

$ git branch -m test-branch readme-updates

$ git branch
* main
  readme-updates
```

Deleting a branch deletes the ref, and Git will refuse if the branch has commits that aren't reachable from the current branch, because deleting the ref would make those commits unreachable.

```
$ git branch -d readme-updates
error: the branch 'readme-updates' is not fully merged
hint: If you are sure you want to delete it, run 'git branch -D readme-updates'
hint: Disable this message with "git config set advice.forceDeleteBranch false"

$ git branch -D readme-updates
Deleted branch readme-updates (was 5c9d5db).
```

Notice that Git tells you what the branch pointed to as it deletes it. That's not just politeness. The commit `5c9d5db` still exists in the repository; only the ref is gone. If you deleted the wrong branch, `git branch readme-updates 5c9d5db` puts it right back, and if you've already lost the hash, *Recovering lost commits* will show you how to find it.

## `git switch` versus `git checkout`

If you learned Git before 2019, you'll have used `git checkout` for all of this. `git checkout` still works, but it does two unrelated jobs (switching branches and restoring files) with the same command, and the combination is responsible for an entire genre of accidents: `git checkout foo` switches to the `foo` branch if one exists, and silently discards your changes to the `foo` file if it doesn't. `git switch` only switches branches, `git restore` only restores files, and this guide uses them throughout. The old commands map directly:

* `git checkout branch` is `git switch branch`.
* `git checkout -b branch` is `git switch -c branch`.
* `git checkout hash` is `git switch --detach hash`.
* `git checkout -- file` is `git restore file`.
* `git checkout HEAD -- file` is `git restore --source=HEAD file`.
