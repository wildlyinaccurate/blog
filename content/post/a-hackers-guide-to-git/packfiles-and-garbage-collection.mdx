Back in *Objects* we saw that Git stores each object as a zlib-compressed file in `.git/objects`. That's simple and it's what Git does for every new object, but it wouldn't scale: a repository with a million objects would have a million small files, and since every version of every file is a separate blob, most of those files would be nearly identical to some other file. Git has a second storage format for exactly this reason, and a process that periodically converts one into the other.

<CarbonAd />

The repository from the previous chapter has a handful of loose objects.

```
$ git count-objects -v

```

`git gc` is Git's housekeeping command. Git runs it for you automatically every so often (which is what the "Auto packing the repository" message you occasionally see is about), but we can run it by hand.

```
$ git gc

$ git count-objects -v
count: 0
size: 0
in-pack: 14
packs: 2
size-pack: 3
prune-packable: 0
garbage: 0
size-garbage: 0

$ ls .git/objects/pack/
pack-60461f6cea5dc96c492c48a3c51b40fc837741c1.idx
pack-60461f6cea5dc96c492c48a3c51b40fc837741c1.pack
pack-60461f6cea5dc96c492c48a3c51b40fc837741c1.rev
pack-f56902331de8f8d596486c7c287147146deb42ab.idx
pack-f56902331de8f8d596486c7c287147146deb42ab.mtimes
pack-f56902331de8f8d596486c7c287147146deb42ab.pack
pack-f56902331de8f8d596486c7c287147146deb42ab.rev
```

All fourteen loose objects are gone, and in their place are two *packfiles*. A `.pack` file contains many objects concatenated together, and its `.idx` companion is an index that maps each object's hash to its offset in the pack, so Git can find an object without reading the whole file. (The `.rev` file is the same mapping in the other direction.) `git verify-pack` lists what's inside.

```
$ git verify-pack -v .git/objects/pack/pack-60461f6*.idx

e59893378579d2ea4b0dad5358c98005b073029e blob   26 36 684
700fe30fe76a4be3e6b1c14213187e6480c1d977 tree   69 77 720
9722ffe2a79ad821e1322518bae35ed15a8e2545 tree   34 45 797

8ef262b9035459f3ef0d2a85300fce7f8e85ea28 blob   23 33 886
543b9bebdc6bd5c4b22136034a95dd097a57d3dd tree   34 45 919
non delta: 11 objects
```

The columns are the hash, type, uncompressed size, size in the pack, and offset. The interesting thing about packfiles is the thing this tiny repository is too small to show: *deltas*. When Git packs objects, it looks for objects that resemble each other (the last ten versions of the same file, say) and stores most of them as a small diff against another object in the pack. It's the only place in Git where anything is stored as a difference, and it's an implementation detail of the storage layer; every command above it still sees whole snapshots. This is how Git manages to store every version of every file and still be smaller than the checkout of a large project.

![Loose objects are stored one per file. A packfile stores many objects together, some as deltas against others, with an index alongside.](/uploads/a-hackers-guide-to-git/packfile.svg)

Packfiles are also what travels over the network. When you push or fetch, the sending side builds a packfile containing just the objects the other side is missing, which is why `git push` prints lines about "Compressing objects" and "Writing objects".

## Unreachable objects

Why two packs? Look at the second one.

```
$ git verify-pack -v .git/objects/pack/pack-f569023*.idx
0f6efe89236a7af4cb61b1cc071ae90dbc6b00d5 commit 244 163 12
878ea3845b42e24ba83174422bbc5a47b2e1b610 tree   108 112 175
e9c96da8580e3c77460dd65d16c4df766ab0840e blob   10 19 287
non delta: 3 objects
```

That's the "Add a feature" commit we deleted the branch for in the previous chapter, along with its tree and blob. It's unreachable, but `git gc` didn't delete it. Instead it put it in a separate *cruft pack*, whose `.mtimes` file records when each object was last seen. The commit is still there.

```
$ git fsck --lost-found
dangling commit 0f6efe89236a7af4cb61b1cc071ae90dbc6b00d5

$ git cat-file -t 0f6efe8
commit
```

Git only actually deletes an unreachable object once two things are true. It has to be older than `gc.pruneExpire`, which defaults to two weeks, so that an object created a moment ago by a command that's still running is never deleted out from under it. And it has to be unreachable from the reflog as well as from the refs, and reflog entries only expire after `gc.reflogExpireUnreachable` (30 days) or `gc.reflogExpire` (90 days). In other words, **a commit you've made is safe for at least a month** no matter how you lose it, and probably three.

We can force the issue, just to prove it's the reflog and the expiry keeping the commit alive.

```
$ git reflog expire --expire=now --all

$ git gc --prune=now

$ git fsck --lost-found

$ git cat-file -t 0f6efe8
fatal: Not a valid object name 0f6efe8
```

Now it's really gone. Please don't do this outside a demonstration; the reflog and the grace period are what make everything in the previous chapter work.

## Maintenance

`git gc` does more than pack objects. It packs refs (which is where `packed-refs` comes from, as we saw in *References*), expires old reflog entries, and writes the *commit-graph*, a cache of commit metadata that lets `git log` and friends walk history without decompressing every commit object.

```
$ ls .git/objects/info/
commit-graph
packs
```

On a large repository the automatic `gc` can take a noticeable pause at an inconvenient moment. `git maintenance start` registers the repository with your operating system's scheduler (launchd, systemd or the Windows task scheduler) so that these tasks run in the background on a schedule instead. If you work on anything with more than a few thousand commits, it's worth turning on and forgetting about.
